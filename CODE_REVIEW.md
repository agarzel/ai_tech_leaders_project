# Code review rules

How pull requests in DevMentor are reviewed – by humans and by `om-code-review` / `om-auto-review-pr`, which apply this file automatically. It complements the full standards in `.ai/docs/engineering-standards.md` (whose code review checklist also applies) and the rules in `AGENTS.md`.

## Review priorities

Review in this order and report findings in the same order:

1. **Correctness** – the change does what the issue or spec asks, including empty, error and permission paths.
2. **Security** – auth and ownership are enforced server-side, input is validated, nothing secret leaks.
3. **Contracts** – nothing listed in `BACKWARD_COMPATIBILITY.md` breaks without the required path.
4. **Architecture and conventions** – the repo-specific checks below.
5. **Tests and evidence** – coverage, integration tests and screenshots where required.
6. **Readability** – naming, size, dead code.

## Validation gate

The PR must pass, in order: `npm run lint`, `npm run typecheck`, `npm run test:coverage`, `npm run build`, `npm run test:integration` (the same list as `.ai/agentic.config.json`). CI additionally runs the migrations check (`db:migrate` on an empty database + `db:migration:check`) and builds the Docker image. A red or missing required check is a **blocker**, reported together with the code findings.

## Repo-specific checks

### Architecture

- Dependency direction `app → core → db`; `ui` imported only by `app`. Only `@devmentor/db` imports `@mikro-orm/*`; `core` never imports `next`/`react`; `app` never imports `@devmentor/db`. Do not accept an ESLint rule being loosened or disabled to make an import pass.
- Domain code lives in concept folders with the same name in every layer (`entities/<concept>/`, `services/<concept>/`, `validators/<concept>/`, `api/<concept>/`). No `modules/`, no auto-discovery, no empty pre-scaffolded folders.
- Every new service is registered explicitly in `packages/core/src/container/container.ts` (`asClass(X).scoped()`), typed in `cradle.ts` and exported from `packages/core/src/index.ts`.

### API routes (`packages/app/src/app/api/**`)

- Plain CRUD uses `makeCrudRoute` (defined once in `<resource>.crud.ts`, re-exported by `route.ts` and `[id]/route.ts`) with an explicit `access`; workflows use `apiHandler`. A route with its own `try/catch` or a hand-built `Response.json` is a **major** finding.
- Input is parsed with the shared Zod schema from `@devmentor/core/validators/<concept>/`; schemas are never redefined in the app.
- Routes contain wiring only – validation → access check → service call. Business rules in a route handler are a **major** finding.
- Endpoints that are not public must enforce access server-side. Until auth exists, admin routes go through `requireAdmin()` (fails closed in production). Hiding a button in the UI is not access control.

### Services and database

- Services return DTOs, never entities, and throw `AppError` subclasses (`ValidationError`, `NotFoundError`, `ConflictError`, …) – never build HTTP responses.
- Writes assign explicitly named fields from parsed input; spreading a request body into `em.create`/`em.assign` (mass assignment) is a **blocker**.
- Request handling uses the request-scoped `em` from `createRequestScope()`, never the global `orm.em`.
- Check-then-write on shared state (slots, bookings, payments) runs in a transaction and/or relies on a unique constraint.
- Entity change ⇒ migration in the same PR, generated by `npm run db:migration:create` and **read**: a table or column rename is generated as drop + create and must be rewritten as `alter table … rename`. Editing an already merged migration is a **blocker**.
- Entities use `defineEntity`, `...baseProperties()`, plural snake_case table names, and are listed in `entities/index.ts`.

### Rendering and UI

- Server code that reads the database or request data calls `await connection()` first; pages wrap it in `<Suspense>`. `export const dynamic` is not used (Cache Components).
- Client components fetch only via `apiCall`/`apiCallOrThrow`; a raw `fetch` to `/api/*` is a **major** finding.
- Forms use `CrudForm`, lists use `DataTable`, loading/error/empty states use the `feedback/` components – a bespoke version needs a reason in the PR description.
- shadcn primitives in `packages/ui/src/components/ui/` are added with the shadcn CLI, not hand-written. Client components import only client-safe entry points (`@devmentor/core/validators/*`, `@devmentor/db/constants`, `import type`).
- Accessibility: controls have accessible names; repeated row actions have unique names (`aria-label="Delete {name}"`); one live region per status.

### Configuration, logging, secrets

- New environment variables are added to the Zod schema in `packages/core/src/config/env.ts` and to `.env.example`.
- Logging goes through the injected `logger` (pino with redaction), not `console.*`, and never includes passwords, tokens, cookies or full JWTs.
- No secrets in code, tests, fixtures, PR descriptions or logs.

### Tests

- `core`, `db` and `ui` keep 100% unit coverage (statements, branches, functions, lines). Lowering thresholds, adding coverage-ignore comments or widening the coverage `exclude` list is a **blocker**.
- Tests are colocated (`*.test.ts(x)`), test behaviour through the public API and mock only boundaries.
- A new page or user-facing flow comes with an integration test of its main path and a screenshot (`packages/app/tests/integration/`).
- A bug fix ships with a regression test that fails without the fix.

### Docs and process

- New conventions, commands, folders or tools are documented in `AGENTS.md` (root or package) in the same PR.
- Non-trivial features have a spec in `.ai/specs/` and a run log in `.ai/runs/`; lessons worth keeping go to `.ai/lessons.md`.
- The PR diff traces entirely to its stated purpose – no drive-by renames or formatting passes.

## Severity guidance

| Severity | Meaning | Examples |
|---|---|---|
| **Blocker** | Must be fixed before merge | failing required check; missing server-side auth/ownership check; mass assignment; secret in code or logs; data-losing migration; edited merged migration; broken contract without the required path; coverage gate weakened |
| **Major** | Fix before merge unless a maintainer waives it on the PR | business logic in a route; hand-rolled try/catch or fetch; missing tests for new behaviour; missing integration test for a new page; dependency-direction violation hidden behind an eslint-disable |
| **Minor** | Should be fixed; may become a follow-up issue | naming off-convention; missing doc update; bespoke component where a shared one fits |
| **Nit** | Optional polish | wording, small readability tweaks |

The verdict is **request changes** when any blocker or major finding is open, otherwise **approve** (listing minors and nits). Labels follow `SDLC.md`.
