# Audit log of admin and operator actions (#119, threat model T-09)

## 📝 TLDR

Every admin and operator action that changes who can do what – role change, user delete, mentor invitation, password set from the CLI – and every failed login leaves an append-only `audit_events` row and the same entry as a structured pino line. Admins read the history on `/admin/audit`.

## 📝 Problem Statement

T-09 (Repudiation, A09:2025, CWE-778): an admin can promote a user, change roles, delete users or invite mentors, and an operator can run `npm run auth:set-password -- --admin`, and nothing records who did it and when. Only booking transitions, the sweep and the health check log today.

## 📝 Proposed Solution

- A new append-only table `audit_events`, written in the same database flush as the change it records, so a rolled-back change leaves no entry and a failed entry write fails the change (fail closed).
- After the flush succeeds, the same entry is logged through the injected pino `logger` (`{ audit: entry }`, level `info`), so the operational log keeps the trail too.
- A read-only, admin-only list: `GET /api/admin/audit-events` and the page `/admin/audit`.

**Answer to the issue's open question ("logs only, or an `audit_events` table?"):** both. Decided by the owner for this task: the history must be readable in the admin panel without server log access.

## 📝 Architecture

- `db`: entity `AuditEvent` + one migration.
- `core`: `AuditService` (`record`, `emit`, `list`) registered in the container; `UserService`, `AuthService` and `InvitationService` call it. `makeCrudRoute` passes the acting session to the service as a `CrudContext`; its access guards are typed to return the `Session` (today `Promise<unknown>`).
- `app`: route `api/admin/audit-events/route.ts`, page `admin/audit/page.tsx`, card on `/admin`.
- `ui`: `AuditLogTable` (DataTable + plain-word formatting) and `describeAuditEvent()`; stories and tests.

Extension mode: additive. No existing route, field, status code or column changes.

## 📝 Data Model

`audit_events` (entity `AuditEvent`, `defineSingletonEntity`):

| Column | Type | Notes |
|---|---|---|
| `id` | uuid PK | `baseProperties()` |
| `created_at`, `updated_at` | timestamptz | `baseProperties()`; never updated by the app |
| `occurred_at` | timestamptz | from the injected `Clock`; indexed, and `(action, occurred_at)` for the action filter |
| `actor_kind` | varchar | `"admin"` \| `"cli"` \| `"anonymous"` |
| `actor_user_id` | uuid, nullable | plain column, **no foreign key**; indexed |
| `action` | varchar | one of the actions below |
| `target_user_id` | uuid, nullable | plain column, **no foreign key** |
| `details` | jsonb | ids and roles only |

No foreign keys on purpose: deleting a user must keep its history (no cascade, no `set null` that would erase who it was).

**What is never stored:** names, e-mail addresses (not even hashed – the user id is enough), passwords, tokens, IP addresses. The pino line carries exactly the same fields as the row (no IP either). Rationale: the table is read by every admin, and ids are enough to resolve the current name while the user exists.

### Actions

| Action | When | actorKind | target | details |
|---|---|---|---|---|
| `user.created` | `UserService.create` (an admin can create an admin through `POST /api/users`) | `admin` | the new user | `{ role }` |
| `user.role_changed` | `UserService.update` and the role really changes | `admin` | the user | `{ from, to }` |
| `user.deleted` | `UserService.delete` | `admin` | the deleted user's id | `{ role }` (role at deletion) |
| `invitation.created` | `InvitationService.create` | `admin` | null | `{ invitationId }` |
| `invitation.revoked` | each older open invitation that `create` revokes | `admin` | null | `{ invitationId, replacedBy }` – `create` reads the open invitations for the e-mail with a **locking read** (`LockMode.PESSIMISTIC_WRITE`, re-exported by `@devmentor/db`) and revokes only those ids. A concurrent create for the same e-mail waits on the lock, then PostgreSQL re-checks `revoked_at is null` and it no longer sees those rows – so every revoked invitation has exactly one entry |
| `auth.admin_password_set` | `AuthService.setPassword` with `admin: true` | `cli` | the user | `{ promoted, created }` |
| `auth.password_set` | `AuthService.setPassword` with `admin: false` | `cli` | the user | `{}` |
| `auth.login_failed` | `AuthService.login`, wrong password or unknown e-mail | `anonymous` | the user when the e-mail exists, else null | `{}` |

`promoted` is true when the role was not `admin` before; `created` is true when the account did not exist.

Not recorded (out of scope or no change of power): `update()` that keeps the role (name/e-mail edits), self-registration (always a mentee), rate-limited login attempts (429 – already counted by the limiter; noted as a residual in T-09).

## 📝 API Contracts

- **Unchanged:** `/api/users` (all methods), `/api/admin/invitations`. `CrudService.create/update/delete` gain an optional last parameter `context?: CrudContext` (`{ actorUserId: string }`); `makeCrudRoute` always fills it from the access guard's session. Existing implementations and callers compile unchanged (BACKWARD_COMPATIBILITY.md §1 and §3: additive for the `CrudService` contract).
- `CrudService.create` gains the same optional `context`; `makeCrudRoute` passes it for POST, PUT and DELETE.
- `UserService.create/update/delete` **require** the context at runtime: called without it they throw an `Error` ("UserService.update needs the acting admin") before touching the database, so an admin action can never be recorded without its actor. Only `makeCrudRoute` calls them.
- `BACKWARD_COMPATIBILITY.md` is updated: §1 lists the new route `GET /api/admin/audit-events`; §3 lists the new exports (`AuditService`, `AuditEventDto`, `CrudContext`, `auditEventListQuerySchema`, `AuditEvent`, `AUDIT_ACTIONS`).
- **New:** `GET /api/admin/audit-events?page&pageSize&action&actorUserId` through `apiHandler`.
  - 401 signed out, 403 for mentor and mentee (route `requireAdmin` + service `requireRole`).
  - Query schema `auditEventListQuerySchema` (strict): `page` ≥ 1 (default 1), `pageSize` 1–100 (default 20), `action` one of the actions, `actorUserId` uuid. Anything else → 400 `validation_error`.
  - Response `Page<AuditEventDto>`, newest first (`occurred_at desc, id desc`):
    `{ id, occurredAt, action, actorKind, actor: { id, name, email } | { id, deleted: true } | null, target: same shape | null, details }`.
    Names and e-mails are resolved at read time from `users`; they are never stored.

## 📝 UI/UX

- The ui package cannot import `core` or `db` (ESLint boundaries), so `describeAuditEvent()` keeps its own map of the eight actions and shows "Unknown action" for anything else, never the raw string. Drift check: the integration test imports `AUDIT_ACTIONS` from the client-safe `@devmentor/core/validators/audit/audit-event-list.schema` and the ui labels, and fails when the two key sets differ; it then renders every action and fails on any raw value.
- `/admin` gets a card "Audit log" – "Who changed roles, deleted users and invited mentors." – linking to `/admin/audit`, after Invitations.
- `/admin/audit`: heading "Audit log", a filter "Action" (select: All actions + the eight actions in plain words), and a `DataTable` with columns **When** (`formatDateTime(iso, timeZone)` from `@devmentor/ui/lib/format`, in the viewer's browser zone from `browserTimeZone()`, with the zone named above the table through `formatZoneLabel`, e.g. "Times in Europe/Warsaw, UTC+1"), **Action**, **Actor**, **Target**, **Details**. No new formatting helper is added.
- Plain words – Action column: "User created", "Role changed", "User deleted", "Invitation created", "Invitation revoked", "Admin password set from the CLI", "Password set from the CLI", "Failed login". Details column: "As admin" (created), "mentee → mentor" (role changed), "Was mentor" (deleted), "Replaced by a new invitation" (revoked), and for the admin password set – precedence: "New admin account" when created, else "Promoted to admin" when promoted, else "Already an admin" (a plain reset); "—" for actions with nothing to add.
- Actor / Target: "Name · email" for an existing user, "Deleted user" for an id with no user, "CLI", "Anonymous", "—" for no target. No raw values (`user.role_changed`, `null`, ISO strings) on screen.
- Empty state: "No audit entries yet."; loading and error states from the backend kit.
- 390 px: only the table scrolls horizontally; the page does not.
- Paging: the table uses `DataTable`'s built-in Previous/Next pagination (20 per page), so older entries stay reachable.
- Access: the admin layout (`AdminGate`) guards `/admin/*`, as for `/admin/users`, which calls no guard of its own; the data comes only from the admin-only API, which refuses everyone else.

## 📝 Edge Cases & Failure Scenarios

- `update()` with the same role writes no `user.role_changed` (name/e-mail edits are not audited).
- Deleting a user keeps its entries; the list shows "Deleted user" for that id.
- A failing flush (e.g. e-mail conflict on update, FK restrict on delete) rolls back both the change and the entry; nothing is logged, because `emit` runs only after a successful flush.
- If the audit row cannot be written, the whole flush fails and the admin action fails (fail closed).
- Failed login: the entry is written on its own flush. If that write fails, the error is logged (`logger.error`, no e-mail) and the user still gets the same 401 "Invalid email or password" – never a 500 and never a different message. The write happens for every failed attempt (known and unknown e-mail), so it adds no timing difference between them.
- Unknown e-mail on failed login: `target_user_id` null, no e-mail anywhere.
- **Two admins change the same user's role at once:** two entries; each records the `from` role its own request read and the `to` it wrote; last write wins, as today. No 409: role edits are rare, the team is two founders, and locking would change the role model (out of scope). Accepted residual, written in T-09.
- `pageSize` above 100, `page` 0, unknown `action`, malformed `actorUserId`, unknown query keys → 400.
- Mentor and mentee: 403 on the route; `/admin/audit` refuses them like every `/admin` page; the card is only on `/admin`, which they cannot open.

## 📝 Risks & Impact Review

- **Risk: high** (SDLC.md: login, a schema migration and a shared contract surface – `CrudService` / `makeCrudRoute`). Required evidence, all in this change: a migration up/down test; integration tests for the denied paths and the wrong-role read; the consuming side of the changed contract exercised (`/api/users` POST/PUT/DELETE through the UI and the API); `needs-qa`, no self-QA; and, because `login` and `setPassword` change (SDLC.md: auth), **a second person's review** before merge.
- Rollback plan: the change is additive. **First** run the migration down while its file is still deployed – `npx mikro-orm migration:down --to Migration20261104120044_user_sessions_revoked_at` from `packages/db` (there is no npm script for down) – which drops `audit_events`; **then** revert the PR. No other table changes, no data to restore. Entries written before the rollback are lost with the table – acceptable, they did not exist before.
- Table growth: a handful of rows per admin action plus failed logins. Failed logins are rate-limited (5 per IP+e-mail, 20 per IP per 15 min), which bounds a single honest client to ~80 rows/hour – but the limiters are in memory and key on the client IP, which can be spoofed through `X-Forwarded-For` when no trusted proxy sits in front of the app (threat model T-03). So anonymous growth of this append-only table has **no hard upper bound** until T-03 is closed and a retention job exists; both are named in the T-09 residuals. Retention is out of scope here.
- Privacy: no personal data beyond ids in the table or the log line.

## 📝 Decisions in play

- D-A1: table + log (owner decision, this task).
- D-A2: no FK on actor/target ids (history survives deletes).
- D-A3: no e-mail, not even hashed; no IP.
- D-A4: concurrent role edits are not locked (documented residual).

## 📝 Open Questions

- Q-A1 (non-blocking): should 429 (rate-limited) login attempts be audited too? Default: no, the limiter already bounds them.
- Q-A2 (non-blocking): retention period for `audit_events`. Default: keep everything until a retention task exists.

One phase; the feature is useful only with all writers and the reader.

## 📋 Implementation Plan

1. `db`: `AuditEvent` entity, `AUDIT_ACTIONS` / `AUDIT_ACTOR_KINDS` constants in `@devmentor/db/constants` (client-safe; `@devmentor/core/validators/audit/audit-event-list.schema` re-exports `AUDIT_ACTIONS` for the app and the drift check), migration + snapshot, entity test.
2. `core`: `AuditService` (`record(em, entry)`, `emit(entries)`, `list(session, query)`), container + cradle + index export; `auditEventListQuerySchema`.
3. `core`: `CrudContext` in `crud.ts`; `makeCrudRoute` passes `{ actorUserId: session.id }` to `create`, `update` and `delete`; `UserService.create/update/delete` take the context as a **required** parameter in their own signatures (the compiler catches a direct caller that leaves it out; the runtime check stays as defence), record and emit.
4. `core`: `InvitationService.create` reads the open invitations it revokes, records `invitation.revoked` per id and `invitation.created`; `AuthService.setPassword` and `login` record.
5. `app`: route, page, admin card.
6. `ui`: `describeAuditEvent()`, `AuditLogTable`, stories, tests.
7. Tests: unit (100%), integration `audit-log.int.test.ts` + scenario `.ai/qa/SECURITY/SECURITY-007-admin-actions-are-audited.md`.
8. `docs/security/threat-model.md`: T-09 → Mitigated, with residuals (429 not audited, no retention, concurrent role edits last-write-wins).

### Tests

- Unit (`db`): migration up/down SQL (pattern of `Migration20261031131551…test.ts`); entity metadata.
- Unit (`core`): every action row and log line; same-role update; missing CrudContext throws before any write; revoke only the ids read; rollback (flush throws → nothing emitted); failed login known/unknown e-mail; failed-login write failure keeps the 401; list paging, filters, newest first, one batched user lookup per page, deleted-user resolution, admin-only; schema cases; `makeCrudRoute` passes the session id.
- Unit (`ui`): every action in plain words, every actor/target shape, no raw values; table empty state; filter.
- Storybook: `AuditLogTable` with all actions, empty, deleted actor; a11y in both themes.
- Integration (`audit-log.int.test.ts`, scenario SECURITY-007), real database:
  - admin changes a user's role and deletes another user through `/admin/users`, creates an invitation, then sees the entries on `/admin/audit` in plain words, newest first; every one of the eight actions (the CLI and login ones seeded through their services in test setup) renders without a raw value;
  - a failed login through `/login` still shows "Invalid email or password" and adds one `auth.login_failed` row with no e-mail;
  - a role change that fails in the database (duplicate e-mail on the same PUT) leaves no audit row;
  - access (R6 three checks): signed out → 401; a mentor gets 200 on a route they may use (positive control) and 403 on `GET /api/admin/audit-events`; `POST`, `PUT` and `DELETE` on `/api/admin/audit-events` → 405 (append-only); the admin re-reads the list afterwards and it is unchanged.

### Acceptance criteria

1. Each listed action writes exactly one row (one per revoked invitation) in the same flush as the change, and the same entry is logged after the flush.
2. No row or log line contains a name, e-mail, password, token or IP.
3. `/admin/audit` shows the entries newest first in plain words, filterable by action, usable at 390 px.
4. Only admins can read the list (401/403 otherwise).
5. T-09 in the threat model is updated.
